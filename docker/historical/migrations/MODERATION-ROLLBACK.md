# Schema-safe moderation rollback (v3)

This is a reviewed procedure specification, not deployment authorization. Never restore a pre-migration backup over a live database as an automatic application rollback.

Apply 20261024-forum-write-freeze.sql to the verified legacy role BEFORE any DDL (maintain this fence on partial-chain failure). Then apply the base moderation/grants and privacy/grants, then 20261024-moderation-retention.sql, then 20261024-moderation-role-fence.sql with independently verified legacy_runtime_role and new_runtime_role. Provision a dedicated restricted cashback_hist_moderated_runtime through the secure owner process; never put its password in SQL/source/reports. It must not own tables/routines or inherit an owner/elevated role. The fence preflight rejects same/elevated/owner roles and reverse membership. New role inherits existing non-forum application privileges; only new role receives moderation/forum writes. Old role cannot read raw topic/post tables (avoids exposing pending material through old code). The compatible new-role backend provides filtered reading. Old role retains member reads and the minimal column UPDATE privilege needed for existing bonus row locks. It cannot update profile fields or insert topics/posts/reviews/cases/appeals.

Source localConfiguration allows the new bounded role and requires it when moderation is enabled. Keep synchronize/migrationsRun false. Startup lifecycle rejects installed schema other than 3 and missing schema when moderation is enabled. Prepare and test an image containing the v3 startup gate and HTTP barrier with CASHBACK_FORUM_READ_ONLY=true before production changes. Do not label an unmodified older image as schema-safe.

Rollback order after any committed migration:
1. Close forum writes using the tested backend read-only image/config, with the DB role fence still installed. This includes registration, avatar/profile, rules acceptance, reviews, topics/posts, reports, decisions and appeals. Do not rely on frontend controls. Keep independent authentication/reading/bonus security checks.
2. Verify GET responses and that POST/PATCH/DELETE cannot reach handlers. The service also rejects direct moderation writes in read-only mode. Check schema marker and exact image/role/network/volume identities. Never downgrade a marker or regrant writes to the old role.
3. Prefer a compatible tested image/config. If an unmodified old binary is accidentally started with its old credential, DB privileges prevent forum writes; it may respond with errors rather than a clean 503, so do not use it as the planned public rollback service. Keep it offline. An incompatible new gated binary fails startup rather than listening.
4. Preserve PostgreSQL, avatar volume, pending queue and privacy erasures. Do not DROP tables, reset strikes, run schema.sql or financial migrations. Partial-chain failures stay in maintenance until a reviewed forward repair.
5. If data recovery is necessary, require separate approval and restore to a new isolated destination, verify rows/FKs/indexes/sequence state, apply erasure ledger and reconcile post-backup writes before any separately approved cutover. The tested 21-Oct dump proves recoverability of that snapshot only; it is not fresh coverage of later registrations.

Retention maintenance is owner-only, serialized exclusively against all application moderation writes, holds and erasure. Application writes take the matching shared transaction lock before per-author locks. Open appeals and unexpired documented holds prevent purge; a fresh resolution restarts the evidence interval. Confirmed minimal strikes remain, while expired sensitive text/journal details are removed. material_erased_at prevents republication of cleared evidence. Review minimal sanction linkage annually; immutability never justifies endless retention. Hold expiry/review dates and reference must be reviewed by the controller; no automated production maintenance is enabled by these files.
